===================================================================================
LASP ARCHITECTURE COMPARISON: Ring vs Blelloch
===================================================================================

CURRENT: RING-BASED LASP (Sequential O(P) Communication)
===================================================================================

Timeline (for P=8 GPUs):
Time →

Step 1:  GPU0 ──→ GPU1
Step 2:  GPU0     GPU1 ──→ GPU2
Step 3:  GPU0     GPU1     GPU2 ──→ GPU3
Step 4:  GPU0     GPU1     GPU2     GPU3 ──→ GPU4
Step 5:  GPU0     GPU1     GPU2     GPU3     GPU4 ──→ GPU5
Step 6:  GPU0     GPU1     GPU2     GPU3     GPU4     GPU5 ──→ GPU6
Step 7:  GPU0     GPU1     GPU2     GPU3     GPU4     GPU5     GPU6 ──→ GPU7
Step 8:  GPU0     GPU1     GPU2     GPU3     GPU4     GPU5     GPU6     GPU7 ✓

Total Steps: 8 (= P)
Pattern: GPU i can only proceed after GPU i-1 completes
Communication: Sequential, blocking

Data Flow:
GPU0: b₀           → KV₀ = b₀
GPU1: b₁           → KV₁ = λ^C·KV₀ + b₁
GPU2: b₂           → KV₂ = λ^C·KV₁ + b₂
...
GPU7: b₇           → KV₇ = λ^C·KV₆ + b₇

Time Complexity: O(P) sequential steps
Latency: P × (α + d²/β) where α=network latency, β=bandwidth


===================================================================================
PROPOSED: BLELLOCH PARALLEL PREFIX SCAN (Logarithmic O(log P) Communication)
===================================================================================

UP-SWEEP PHASE (Build partial sums)
-----------------------------------

Level 0 (Initial): All GPUs start in parallel
GPU0: b₀    GPU1: b₁    GPU2: b₂    GPU3: b₃    GPU4: b₄    GPU5: b₅    GPU6: b₆    GPU7: b₇

Level 1 (Stride=1): 4 parallel communications
GPU0 ──→ GPU1: s₁ = λ^C·b₀ + b₁
GPU2 ──→ GPU3: s₃ = λ^C·b₂ + b₃
GPU4 ──→ GPU5: s₅ = λ^C·b₄ + b₅
GPU6 ──→ GPU7: s₇ = λ^C·b₆ + b₇

Level 2 (Stride=2): 2 parallel communications
GPU1 ──→ GPU3: s₃ = λ^(2C)·s₁ + s₃  [covers GPUs 0-3]
GPU5 ──→ GPU7: s₇ = λ^(2C)·s₅ + s₇  [covers GPUs 4-7]

Level 3 (Stride=4): 1 communication
GPU3 ──→ GPU7: s₇ = λ^(4C)·s₃ + s₇  [covers GPUs 0-7, TOTAL SUM]

DOWN-SWEEP PHASE (Distribute prefix sums)
------------------------------------------

Level 3 (Stride=4): 1 communication
GPU7 ──→ GPU3: Send prefix for left subtree

Level 2 (Stride=2): 2 parallel communications
GPU7 ──→ GPU5: Send prefix
GPU3 ──→ GPU1: Send prefix

Level 1 (Stride=1): 4 parallel communications
GPU7 ──→ GPU6: KV₆ ✓
GPU5 ──→ GPU4: KV₄ ✓
GPU3 ──→ GPU2: KV₂ ✓
GPU1 ──→ GPU0: KV₀ ✓

Final State: All GPUs have their prefix sum
GPU0: KV₀ = b₀
GPU1: KV₁ = λ^C·b₀ + b₁
GPU2: KV₂ = λ^(2C)·b₀ + λ^C·b₁ + b₂
...
GPU7: KV₇ = λ^(7C)·b₀ + λ^(6C)·b₁ + ... + b₇

Total Steps: 3 (up-sweep) + 3 (down-sweep) = 6 (= 2·log₂(8))
Pattern: Tree-based, multiple parallel communications per level
Communication: Parallel within each level

Time Complexity: O(log P) levels
Latency: 2·log₂(P) × (α + d²/β + contention_factor)

===================================================================================
HYBRID STRATEGY (Best of Both Worlds)
===================================================================================

For 128 GPUs on 16 nodes (8 GPUs per node):

Phase 1: BLELLOCH WITHIN NODES (O(log 8) = 3 steps)
────────────────────────────────────────────────────

Node 0:  GPU0-7   → Blelloch scan → node_KV₀
Node 1:  GPU8-15  → Blelloch scan → node_KV₁
Node 2:  GPU16-23 → Blelloch scan → node_KV₂
...
Node 15: GPU120-127 → Blelloch scan → node_KV₁₅

Communication: Fast NVLink/NVSwitch (low latency, high bandwidth)
Steps: 3 (up-sweep) + 3 (down-sweep) = 6

Phase 2: RING ACROSS NODES (O(16) = 16 steps)
──────────────────────────────────────────────

Node0 ──→ Node1 ──→ Node2 ──→ ... ──→ Node15

Communication: Slower InfiniBand (higher latency)
Steps: 16

Phase 3: BROADCAST WITHIN NODES (O(1) step)
────────────────────────────────────────────

Each node broadcasts inter-node result to all local GPUs

Total Steps: 6 (intra-node) + 16 (inter-node) + 1 (broadcast) = 23
vs Pure Ring: 128 steps
vs Pure Blelloch: 14 steps (but with high contention)

Hybrid Advantage: Balances speed and stability

Pseudocode:
    KV = zeros(b, h, d, e)

    # Receive from left neighbor
    if rank > 0:
        dist.recv(KV, src=rank-1)

    # Compute local contribution
    kv_local = compute_local_kv(k, v)
    KV = block_decay * KV + kv_local

    # Send to right neighbor
    if rank < world_size - 1:
        dist.send(KV, dst=rank+1)

Characteristics:
- Simple 3-line communication pattern
- Sequential dependency (must wait for left neighbor)
- Single send/recv per GPU per forward pass
- No tree management overhead


BLELLOCH IMPLEMENTATION (Proposed):
────────────────────────────────────

File: lasp/lasp_blelloch.py (new)

Pseudocode:
    local_b = compute_local_kv(k, v)
    tree_values = [local_b]

    # UP-SWEEP: Build tree bottom-up
    for level in range(log2(P)):
        stride = 2^level
        if rank % (2*stride) == 0:
            # Send to right child
            dist.send(tree_values[-1], dst=rank+stride)
        elif rank % (2*stride) == stride:
            # Receive from left child and combine
            received = dist.recv(src=rank-stride)
            combined = decay^stride * received + tree_values[-1]
            tree_values.append(combined)

    # DOWN-SWEEP: Distribute prefixes top-down
    prefix_sum = None
    for level in range(log2(P)-1, -1, -1):
        stride = 2^level
        if rank % (2*stride) == stride:
            # Receive prefix from parent
            left_prefix = dist.recv(src=rank-stride)
            prefix_sum = decay^stride * left_prefix + tree_values[level]
        elif rank % (2*stride) == 0:
            # Send prefix to right child
            dist.send(prefix_sum, dst=rank+stride)

    return prefix_sum

Characteristics:
- Complex tree traversal logic
- Multiple rounds (2·log₂(P))
- Different communication partners per level
- Requires tree value storage
- Parallel communications within each level


===================================================================================
KEY MATHEMATICAL INSIGHT
===================================================================================

Why Blelloch Works: ASSOCIATIVITY
──────────────────────────────────

The KV recurrence:
    KV[t] = λ^C · KV[t-1] + b[t]

Can be rewritten as an associative operator:
    (A₁, b₁) ⊕ (A₂, b₂) = (A₁·A₂, A₂·b₁ + b₂)

For LASP:
    A = λ^C    (scalar decay)
    b = KV     (d×d matrix)

Associativity proof:
    ((A₁,b₁) ⊕ (A₂,b₂)) ⊕ (A₃,b₃)
    = (A₁·A₂, A₂·b₁+b₂) ⊕ (A₃,b₃)
    = (A₁·A₂·A₃, A₃·(A₂·b₁+b₂)+b₃)
    = (A₁·A₂·A₃, A₃·A₂·b₁ + A₃·b₂ + b₃)

    (A₁,b₁) ⊕ ((A₂,b₂) ⊕ (A₃,b₃))
    = (A₁,b₁) ⊕ (A₂·A₃, A₃·b₂+b₃)
    = (A₁·A₂·A₃, (A₂·A₃)·b₁ + A₃·b₂ + b₃)
    = (A₁·A₂·A₃, A₃·A₂·b₁ + A₃·b₂ + b₃)  ✓ SAME!

This associativity is the ONLY reason parallelization is possible.
Without it, we're stuck with O(P) sequential computation.

===================================================================================
WHEN TO USE WHICH STRATEGY
===================================================================================

Decision Tree:
──────────────

GPU Count (P):
│
├─ P < 16
│  └─→ USE RING
│      Reason: Simple, low overhead, Blelloch gains minimal
│
├─ P = 16-32
│  └─→ USE BLELLOCH
│      Reason: 2-3× speedup, contention manageable
│
├─ P = 32-64
│  └─→ USE BLELLOCH (if good network) or HYBRID
│      Reason: 3-5× speedup, test both on your hardware
│
└─ P ≥ 64
   └─→ USE HYBRID
       Reason: Best balance of speed + stability
       └─ Unless: Single-node DGX → Pure Blelloch

Network Quality:
│
├─ Fast (NVSwitch, NVLink within node)
│  └─→ Prefer BLELLOCH
│
├─ Medium (InfiniBand, cloud)
│  └─→ Prefer HYBRID
│
└─ Slow (Ethernet, distributed)
   └─→ Stick with RING
